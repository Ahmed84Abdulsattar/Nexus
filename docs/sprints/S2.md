## 1. Scope
S2 delivers the top level of Nexus: the DATOMS client (the only DATOMS caller code), the projects API, the ArcGIS portfolio map with its list, tiles and filters, and the users-and-roles API. All of it is fed by DATOMS, Entra ID and ArcGIS only.

- **Backend (Ahmed):** S2-01 projects API, S2-02 DATOMS client (PR #11), S2-06 users and roles API.
- **Frontend (colleague):** S2-03 portfolio map, S2-04 list and tiles, S2-05 search and filters.
- **Carried in this file:** the S3-01 phase 1 questions (section 8). That branch is stacked on S2-02, and its answers change schema and docs that S2 reviewers will see.
- **What S2 can show today.** DATOMS has **no site fields yet** (Q21, Q22). The S2-02 live test showed that bulk rows carry only `asset_id`, `success` and `data {time, parameters}`. So no project can come from DATOMS in S2. The portfolio shows `core.project` rows **as stored**: fictional sample sites in local and dev (S2-01 seed), and, in prod, projects an admin creates (R-63) until the site fields are mapped. See point (a) in section 5 under S2-01.

Status key (as of 2026-10-14): **Done** = merged to `main`. **In review** = PR open. **In progress** = branch exists, no PR yet. **Not started** = no branch. **Blocked** = waiting on something outside the team.

## 5. Task notes (design details and reviews)
Every PR goes through **qa** against its acceptance check and the `14` checklist. Rows marked "security-reviewer: yes" also need that review and a human review (`14` definition of done, item 4).

- **S2-01** (security-reviewer: **yes**: project scope on list, search and counts). **Point (a): what does S2-01 return now?**
  - **It returns `core.project` rows as stored, and nothing about DATOMS.** It does not "return the fields DATOMS provides for each site" (backlog step 3), because DATOMS provides none yet (Q21, Q22) and the bulk rows carry no site (section 2). The response describes the project and where its state came from (`stateOrigin`: `source` or `admin`), never where a field "should" come from.
  - **Local and dev:** `db/seeds/dev-projects.sql` (backlog step 4). Five **fictional** sites (for example "Sample Site A"), not real Innovo names. They cover all five states, including `unknown`, plus one site with no coordinates (tests "Not on map") and one with `null` client, consultant and PM (tests "—"). The seed inserts its own `core.source_system` row (for example `sample`), so sample rows can never collide with DATOMS ids and are easy to spot. That row is environment data in the seed, not reference data in the schema. The runner refuses this seed when `APP_ENV=prod`.
  - **Prod:** empty until either (1) admins create projects through R-63 (`/v1/admin/projects`, `10`), or (2) the bulk site fields are mapped (Q21, Q22). **R-63 has no backend row in the backlog** (`02` maps it to S3-05, which is the frontend linking page), and admin-created projects need a decision on project identity (proposed ADR 0012, section 6). See gap G3. Until then prod shows the empty state "No projects assigned to you", which is the truth.
  - **R-10's acceptance check ("every DATOMS site the user has access to appears") cannot be met in S2.** It moves to the task that maps site fields (S3-01/S3-03, after Q21/Q22) or to R-63 for the pilot.
  - **Summary counts are project data too.** `/projects/summary` must go through `withProjectScope`, or the district counts reveal projects the user cannot see (R-03).
  - `type` filter values and summary type counts come from `project_type` data (hard rule 3). `district` is filtered by district id.
- **S2-02** (security-reviewer: **yes**, done in PR #11). Remaining review items:
  - The doc corrections in section 2: `07` §3.2 ("18" is `category_id`; 8 DG sets), the seed comment, Q34 answered, the Q35 update, and the ADR 0011 facts-only line.
  - **Fixtures come from Innovo's live org** (`07` §4 item 9). Check that they hold no token, header or personal data before merge. Asset names may contain real site names, which is acceptable for an internal repo but should be a conscious choice.
  - `budget.max_share` and `poll.subset_external_ids` are passed **into** the client as config by the worker. `datoms-client` never reads the database.
- **S2-03** (security-reviewer: no; it adds no credential handling; the key path is S0-09 and S1-10). **Point (b):**
  - The ArcGIS key (Q4, Q23) blocks only the checks that need real tiles: the real-basemap screenshot and the 60 fps pan (R-12). Everything else is logic in the wrapper and the feature, testable with the adapter's tile requests stubbed, as `09` §7 already asks ("network stubs for tiles in the rest").
  - **Recommendation (D3):** merge on part A; record part B as "deferred acceptance (Q23)" in the PR and on S0-09; run both in one session when the key arrives.
  - The backlog's "click a pin = zoom to that project" and `09` §3 / R-12 ("summary popup, then open the project page") are reconciled by S1 decision D1: a click selects the project, the map zooms or centres, and the details panel acts as the popup with "Open project". Update `09` §3 in this PR. If S1 D1 goes the other way, use the ArcGIS popup as `09` §3 describes now.
  - Pin colour reflects stored `state`. With no DATOMS site data, prod pins are admin-set or `unknown` (neutral). Never colour a pin from anything else (R-11).
- **S2-04** (security-reviewer: no). **Point (b), Q18:** the mockup's "client, consultant, PM" columns depend on Q18. **Do not block on it:** render what the API returns, and show "—" for `null`. If Innovo answers "admins maintain them", only the R-63 admin fields grow (backend); S2-04 does not change. If they come from DATOMS, only `mapping.ts` and the catalogue change. If they are dropped, remove the columns then. Narrow the acceptance check to "shows the API value or '—'" (done in the table). Summary tiles follow R-13 ("by state and district"), not the backlog's "number of projects, number of districts".
- **S2-05** (security-reviewer: no). Search is server-side (`q` → trigram `ILIKE`, `06` §7) so it stays fast and scoped at 500 sites; never filter a full client-side list as the source of truth. Optional and small: the S1-05 header search box can navigate to `/` with `?q=`. Do it only if Ahmed agrees; it is not in the backlog.
- **S2-06** (security-reviewer: **yes**).
  - **"Endpoint listing Entra groups" is not possible without Microsoft Graph**, which ADR 0008 removed. List the **mapped** groups (`access.group_role`, with the admin-typed `group_name`) and, if D5 is accepted, the group ids seen in tokens.
  - **Showing each user's roles (R-60, S3-07) needs the user's groups,** and Nexus only sees them in tokens. Recommendation (D5): add `access.app_user.last_group_ids uuid[]` and `groups_seen_at`, written **only on an access-cache miss and only when changed** (no per-request writes). The same data powers the `08` §1 warning "mapped group not in any token seen". This is an additive migration with no ADR. Update `06` §1 and `08` §1.
  - **"Keep room for extra permissions"** means new permission keys are added by migration and granted to roles (`08` §3). There are no per-user permission grants. `access.user_role` (direct role) stays a break-glass path, managed by runbook, not by an endpoint in phase 1.
  - **Deactivating a user** (`is_active`) has no endpoint in `10`. The off-switch is removing the user from the Entra group (assignment required). Not built in S2.
  - **Invalidation:** a group-role change or a group grant calls `invalidateAll`; a user grant calls `invalidateUser`. Both go through S1-01's cross-instance mechanism.
  - Deleting `group_role` and `project_access` rows is allowed. They are Nexus configuration, not synced rows (hard rule 8 covers synced rows), and every delete is audited with the old values.

**ADRs**

- **Proposed ADR 0012 · Identity of Nexus-held projects (needed before the R-63 backend task and S3-02; not needed for S2-01).**
  - **Problem:** `core.project` requires `source_system` and `external_id` (NOT NULL, unique together). An admin-created project (R-63) has no source identity. When DATOMS site fields arrive, the admin-created GHAFWOODS must be joined to the DATOMS site without deleting or duplicating it (hard rule 8). In phase 2 one Nexus project will also be a site in other systems (HSE, materials; `13`).
  - **Options:**
    - (A) A `nexus` row in `core.source_system`. Admin projects use their own id as `external_id`, and linking a DATOMS site **replaces** the identity, while `state_origin = 'admin'` keeps admin fields safe.
    - (B) The project is Nexus-owned, and a link table `core.project_source_link (project_id, source_system, external_id, linked_by, linked_at)` holds one row per source identity. The source columns move off `core.project` or become nullable.
  - **Architect's lean: (B).** It matches "a project is fed by many sources" (`13`, connector pattern), keeps every source id forever, and makes the S3-02 auto-link an insert, not an identity change. It is a structural change to a core table, so it needs the ADR and Ahmed's decision.
  - S2-01 does not wait for it: the dev seed uses its own `sample` source system.
- **No ADR** for the (d) answers in section 8, for D5 or for D7. They are additive columns or doc corrections inside existing decisions. D7 gets a facts-only update line on ADR 0010, because the asset category now comes from the catalogue, while telemetry stays bulk-only.
