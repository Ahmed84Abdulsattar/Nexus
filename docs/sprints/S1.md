## 1. Scope
S1 builds the foundation that every phase 1 screen stands on. All of it serves the three phase 1 sources: DATOMS data lands in the S1-01 tables, Entra ID identities are checked by S1-02, S1-04, S1-08 and S1-09, and the ArcGIS map sits in the S1-05/S1-06 shell.

- **Backend (Ahmed):** database and migrations (S1-01), the API guard (S1-02, done), the OpenAPI contract (S1-03, done), the audit log (S1-04) and the API baseline protections (S1-09).
- **Frontend (colleague):** header (S1-05), responsive layout (S1-06), loading/empty/error states (S1-07) and role-filtered navigation (S1-08).
- **Proposed addition: S1-10, `GET /v1/me` and `GET /v1/config`.** The S0 plan expected both in S1-02 (S0.md sections 5 and 7). S1-02 was merged without them, and no backlog row owns them now. S1-08 (navigation by permission) and the real ArcGIS key (S0-09, S0 decision 1) need them. See gap G1 in section 5 and decision D2 in section 8.
- **No DATOMS calls in S1.** S1 makes no DATOMS calls and changes no DATOMS code. The DATOMS client is S2-02 (PR #11). S1-01 only creates the tables and the dev settings (`poll.subset_external_ids`, `budget.max_share`) that ADR 0005 requires.

Status key (as of 2026-10-14): **Done** = merged to `main`. **In review** = PR open. **In progress** = branch exists, no PR yet. **Not started** = no branch. **Blocked** = waiting on something outside the team.

## 4. Task notes (design details and reviews)
Every PR goes through **qa** against its acceptance check and the `14` checklist. Rows marked "security-reviewer: yes" also need that review and a human review (`14` definition of done, item 4).

- **S1-01** (security-reviewer: **yes**: roles, grants, DB credentials, access cache, project scope).
  - The migration must produce exactly `db/schema.sql`. Initial partitions are created relative to `current_date`, so `db:check` excludes partition children (`06` §8 rule 4).
  - **Partitions run out.** The schema creates 9 days of daily partitions (`telemetry.packet`, `integration.api_call`) and 3 months of monthly ones (`audit.log`, `events.event`, …). Nothing keeps them rolling until the worker's maintenance job exists, and that job has no backlog row (gap G2, section 5). This is fine locally. It must be fixed before any deployed environment runs the worker for more than a week.
  - **Cache invalidation.** If it uses `LISTEN/NOTIFY`, each API instance needs a dedicated listening connection, and on reconnect it must clear its **whole** cache, because notifications sent while it was disconnected are lost. A per-user access version, checked on a cache hit, works without that but costs one cheap query per request. Either meets backlog step 6; record the choice in `08` §2 "Known limits".
  - **Env vars.** `04` keeps one list. It says `DATABASE_URL` for api, worker and migrations, so adding `WORKER_DATABASE_URL` and `DATABASE_ADMIN_URL` means updating `04` and `.env.example` in this PR.
  - **Seeds.** `dev-settings.sql` sets `poll.subset_external_ids` and a small `budget.max_share` (ADR 0005); it never runs in prod. `datoms-parameters.sql` runs in every environment (ADR 0011). Sample sites belong to S2-01 (`db/seeds/dev-projects.sql`), not here.
  - **Benchmark.** `scale-100-sites.ts` should generate packets with the real DG Set and AC Sub-Meter keys from `datoms-parameters.sql`, not `p001…p103`, so row sizes are closer to reality. The re-benchmark with real recorded fixtures (`06` §6) needs S2-02's fixtures (PR #11), which are not on `main`. It has no owner yet (gap G4, `S2.md`).
- **S1-02 / S1-03** (done). Nothing to build. Q29(a) (accept only one `aud`) waits for S0-04.
- **S1-04** (security-reviewer: **yes**: audit content, personal data, admin endpoint).
  - **What counts as a sign-in.** The API is stateless, and access tokens refresh about every hour, so "one row per token" is noise. Recommendation (decision D3): when the access cache misses and the user's previous `last_seen_at` is older than a setting `audit.sign_in_gap_minutes` (default 60, in `core.setting` through a migration), write `auth.sign_in`. If S0-04 shows that `nexus-api` access tokens can carry the `sid` optional claim (proposed question Q38), switch to "first request per `sid`". Either way, update `08` §2 step 6 with the exact rule.
  - Admin changes write their audit row **in the same transaction** as the change. A sign-in row is best-effort: if it fails, log it and don't fail the request.
  - `audit.log` is partitioned monthly, so the read endpoint always has a time window. The audit log is kept 2 years (N-10).
  - Action names (`auth.sign_in`, `admin.group_role.create`, `explorer.export_csv`, …) are Nexus's own vocabulary. They live as constants in `packages/shared`. This is not source data, so hard rule 3 doesn't apply.
- **S1-05** (security-reviewer: no). The header must not show anything Nexus doesn't have: no unread count until S6-08, and no fake search results. The header search has no backend in phase 1 beyond the portfolio `q` filter. A sensible later use is "search box → `/` with `?q=`" (S2-05 note).
- **S1-06** (security-reviewer: no). **Layout conflict (point c):**
  - `docs/11` says the portfolio list is a **right** side panel, the project page on a tablet is "map on top, boxes in a 2-column grid", and the phone portfolio uses map/list tabs with a bottom sheet.
  - Backlog S1-06 says "list panel left, map centre, details panel right (**as mockup**)". PR #15 follows the backlog.
  - **Recommendation (D1):**
    1. **The brief mockup outranks both texts.** The frontend developer attaches the mockup crop to PR #15. The mockup images are in `Nexus_by_Innovo.docx` and not in `brief.md`, so agents cannot check them.
    2. If the mockup shows list left and details right, or is unclear: **keep PR #15 for the portfolio shell and update `docs/11` in PR #15.** The backlog cites the mockup and `docs/11` cites no source. PR #15 has QA PASS. A right-hand details panel is also the desktop counterpart of the phone's "bottom sheet for the selected project" that `docs/11` already describes. S2-03 then shows the selected project in that panel, not in an ArcGIS popup (`09` §3 is updated in S2-03).
    3. **`docs/11` wins for the project page** (desktop: map left about 65% with boxes in a right column; tablet: map on top with boxes in a 2-column grid; phone: map at 50 vh with stacked boxes). That is S4-04's screen. S1-06 only has to give it the slots (acceptance check 5), not a three-pane layout.
    4. **`docs/11` wins for the phone portfolio** (map/list tabs and a bottom sheet). S1-06 provides the bottom sheet; the tabs come with the list in S2-04.
  - Breakpoints in PR #15 (desktop ≥ 1280, tablet 768–1279, phone < 768) match `docs/11`'s `md` and `xl`. Write the three tiers into `docs/11` explicitly.
- **S1-07** (security-reviewer: no). Shows `detail` and `correlationId` from problem+json only. The Forbidden state should rarely appear, because the route guard (S1-08) and the API's 404 for out-of-scope ids handle most cases. Format every timestamp in Asia/Dubai (`11` rule 3, hard rule 9).
- **S1-08** (security-reviewer: no, unless it changes MSAL or token handling). **Point (e): what can be built now?**
  - **Buildable now:** the whole permission model on the web side. That is `usePermissions()`, `<Can>`, nav items declared with permission keys from `packages/shared/src/permissions.ts`, the `/admin/*` route guard, MSW `/v1/me` fixtures for each seeded role, component tests and Playwright with mocked auth. Merge it on MSW.
  - **Blocked:** (1) real sign-in (S0-08: Q16, Q24); (2) typed access to `/v1/me`. `11` requires API types from the generated `schema.d.ts`, and `/v1/me` is not in the OpenAPI yet, which is why S1-10 is proposed. Until S1-10's contract exists, the frontend can build against a hand-written MSW handler, then swap to the generated type in a small follow-up commit in the same PR before merge.
  - **Backlog wording:** "Read the user's roles from the sign-in token" conflicts with `08` §3 and §5. Roles are mapped from groups in the **database**, and the UI reads `GET /v1/me`. The UI hides by **permission**, not by role name, so a Q17 change to the role list needs no frontend change.
- **S1-09** (security-reviewer: **yes**).
  - **Two limits.** (1) An IP limit at the Fastify level for every request, including unauthenticated ones, so 401 floods are capped. (2) A per-user limit **after** `EntraJwtGuard`, keyed on the verified `oid`. Do not key the Fastify hook on an `oid` decoded from an unverified token, because anyone could then spend another user's limit. Values come from env (proposal: `API_RATE_LIMIT_USER_PER_MINUTE` = 600 per `08` §6, `API_RATE_LIMIT_IP_PER_MINUTE`, `API_BODY_LIMIT_BYTES`, `CORS_ALLOWED_ORIGINS`), all added to `04` and `.env.example`.
  - **Per-replica counters.** With N API replicas the real limit is N × the configured one. Accept this (no Redis before the `12` §2 trigger) and write it in `08` §6.
  - **Trusted proxy.** Container Apps sits in front of the API, so set Fastify `trustProxy` to exactly the ingress hop count from config. Otherwise every request looks like it comes from one IP.
  - **Library.** `@fastify/rate-limit` (and `@fastify/helmet`, `@fastify/cors`) are used only in `apps/api`. That fits the "small helper library inside a module" rule in `04`, so no ADR. Add them to the `04` backend table.
  - helmet's default CSP is fine for JSON. Swagger UI exists only in local/dev, and if it needs a looser CSP, apply it to `/docs` only.
- **S1-10** (proposed; security-reviewer: **yes**: the ArcGIS key reaches the browser).
  - The key is a referrer-restricted browser key. It goes only to signed-in users and is never logged.
  - Enums come from the schema's CHECK lists and the database (project states, display statuses, feature flags), never typed into the web app.
  - Once S1-10 is merged and running locally, S0-09's MSW `/v1/config` mock and `VITE_DEV_ARCGIS_API_KEY` can be removed (`04` says "Remove after S1-02"; change it to S1-10).
